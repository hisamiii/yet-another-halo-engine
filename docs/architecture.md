# Architecture

The engine runs one model (Qwen3.8-27B as a llama.cpp GGUF, run in the GGUF's own quant formats; the target is unsloth's UD-IQ4_XS) on one GPU (Strix Halo, gfx1151), with part of a prefill's GEMMs and attention optionally on the NPU. Every kernel is written in Loom and compiled for the exact shapes of this model. Python generators write the Loom source, `emit_hal.py` compiles it to an HRX HAL executable, and two small C++ drivers dispatch the HAL sets through the HRX native API. There is no general tensor runtime: the layer loop is hand-written.

This page describes the model, the prefill pipeline, the decode step, the data layouts and the HAL sets. Numbers are in [results.md](results.md), measured hardware facts in [hardware.md](hardware.md).

The native GGUF sets are the only path. Older paths are in git: the first native engine at tag `pre-cleanup-2026-10-20` (its NPU history on branch `npu`), and the MQ4 path (hipfire's HFQ file, A4 prefill, MTP speculative decoding) at commit be687da, the last before its removal on 2026-11-14.

## The model

Qwen3.8-27B is a hybrid: every 4th layer is full (softmax) attention, the others are Gated DeltaNet (a linear-attention recurrence). `engine/core/config.hpp` reads every field from the file.

| item | value |
|---|---|
| layers | 64 main layers; GGUFs from unsloth add the MTP layer as `blk.64.nextn.*` (`nextn_predict_layers` 1: one full-attention block behind `eh_proj` 10240 -> 5120, sharing the output head); the engine does not load it |
| full-attention layers | 16: layers 3, 7, 11, ..., 63 (`(l + 1) % 4 == 0`) |
| Gated DeltaNet layers | 48 |
| hidden | 5120 |
| FFN | SwiGLU, 17408 |
| attention | 24 query heads, 4 KV heads (GQA 6), head dim 256, RoPE on 64 of 256 dims, per-head QK RMSNorm, sigmoid output gate |
| attention q projection | 12288 rows: per head 256 q rows then 256 gate rows |
| DeltaNet | 16 key heads, 48 value heads, head dim 128, state 128 x 128 per value head, short conv width 4 over 10240 channels (q 2048, k 2048, v 6144), z gate 6144, alpha / beta 48 each |
| vocab | 248320 |
| weights | each tensor in its GGUF format (UD-IQ4_XS: a 13.27 GiB file, projections from IQ2_XXS to Q8_0); at load the token embedding becomes Q8_0 and the norms and small DeltaNet tensors f32 |

### Loading

`engine/core/gguf.cpp` reads the GGUF (`core::Gguf`) and `engine/core/gguf_convert.cpp` presents it as the engine reads it: the projections keep their bytes (the sets run the GGUF's own formats), ffn_up right after ffn_gate (the NPU FFN block reads gate through up rows in one view); token_embd becomes Q8_0, as does an output.weight that is not Q6_K or Q8_0, and the small tensors f32 (`engine/core/gguf_quant.cpp` has the dequantizers). Every kernel works in the GGUF's DeltaNet value-head order. The MTP layer (`blk.64.*`) is skipped. The file is read into anonymous memory (2 MB pages where the kernel has them), range by range as the device uploads it.

The tensors are then copied into device-local HRX buffers of about 1 GiB cut at tensor boundaries (`LoomWeights`), each host range released right after its copy: RAM holds one copy of the model. A mapped file does not work: reclaim and compaction scan its page-cache folios, and every scan of a GPU-imported page evicts all of the process's GPU queues (hardware.md).

## Prefill

`engine/model/loom_prefill.hpp` (`LoomPrefill`) runs a prompt through all 64 layers as one batch of B tokens (B = 2048 by default); `loom_forward_pp` is its command-line driver. Every kernel has the token count in its grid, so there is no per-tile loop. All activations are token-major (`[token][row]`). The residual stream is f32.

The GEMMs run on the f16 WMMA with f16 activations; the weights are decoded from their GGUF format to f16 in LDS (the tile GEMM, below), with the reference dequantization's ops, so every GEMM is bit-identical to a dequantize-then-multiply.

### Kernels per layer

The chunk graph starts with `yah_embed` (`gen_decode_misc.gen_embed_q8_0`, rows = B), which dequantizes the token_embd rows of the chunk's token ids.

Every layer starts with `yah_half_norm` (attn_norm) into f16: row-major (`norm`), fragment-major for afrag GEMMs (`norm_t`, below) or both (`norm_rt`); dispatch.txt `norm_split` gives a row several waves.

Full-attention layer:

1. The norm.
2. attn_q as a `kqg` GEMM (12288 rows): the epilogue writes q and gate to separate buffers; with `qsplit` it stores the split-norm query the attention reads (gen_attn_fa `R2P_QSPLIT`), with `gsig` the gate's sigmoid as unorm16. attn_k and attn_v as `kstore`, or riding in the kqg GEMM's dispatch (`seg_kqg`, segmented GEMMs).
3. `yah_fused_qk_rope_batched` (the k / v form): K RMSNorm and RoPE, K straight into its page of the K pool (`rope_kpaged`), V into the paged V^T tiles (`vtrope`), or the KV quantizers (`yah_kmean` on the first chunk, `yah_kq8` / `yah_kq4`, then `yah_vq8` / `yah_vq4`) for quantized KV.
4. `yah_attn_wmma` (FlashAttention-style, below): the q RMSNorm and RoPE run inside it (`qnorm`).
5. attn_output as a `kres` GEMM: it reads the residual and writes residual + W x into the second hidden buffer; the two swap.

Gated DeltaNet layer:

1. The norm.
2. ssm_alpha and ssm_beta (48 rows each; first, so they read the norm's output before the big GEMMs evict it), attn_qkv (10240 rows) and attn_gate (z, 6144 rows) as `kstore` GEMMs; alpha and beta can ride in the qkv GEMM's dispatch (`seg_kstore`).
3. `yah_ssm_conv_kq` (`gen_conv_kq`): the causal conv of the q / k heads with their L2 normalization, a workgroup per (256 channels, `convtb` tokens).
4. `yah_deltanet` in two parts (dispatch.txt `dnsplit`: heads 0-39, then 40-47). Sets without an NPU qkv split (and not the token-half sets) run the state-stationary kernel (`gen_gdn_ss`: one workgroup per head, the state in registers), which computes the v channels' conv and alpha / beta itself (`dnvconv`; the conv kernel then takes only the q / k heads), and the gate GEMM runs beside the second part, which leaves most of the GPU free. The other sets run the chunked form (`gen_gdn_chunk`, below).
5. `yah_deltanet_prep_ab` advances the conv ring past the real tokens; `yah_ssm_postnorm_fp16`: the gated RMSNorm per head with z.
6. ssm_out as `kres`.

Then the FFN, for every layer: the norm (post_attention_norm), gate and up, ffn_down as `kres`. Gate and up run as one `ffn` GEMM where a fused kernel exists for the layer's pair of formats (`emit_prefill_pp.ffn_fused`: a workgroup stages the gate rows and the same features' up rows, and the epilogue writes f16 silu(gate) x up, so the gate never goes to memory), else as `kstore` gate, then `swiglu` up.

After the last layer of the last chunk: `yah_rmsnorm` on the last token, the output GEMV (`gen_gemv`, 248320 rows) and `yah_argmax`. The last layer's tail runs only the GEMM token tiles holding the rows the caller reads (`RunLayers` keep: the last token, or none on chunks whose output nobody reads).

### The tile GEMM

`tools/gen_gemm_tile.py` with a per-format decoder from `tools/gen_gemm_decode.py` (Q8_0, Q2_K-Q6_K, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_NL, IQ4_XS; the IQ grids bound after the weights):

- Workgroup 128 rows x 256 tokens over 4 x 4 wave32 waves of 32 x 64.
- Per K phase (64), the decoded weight tile and the activation tile are both in LDS, so the MMA loop reads only LDS. LDS rows are padded (+8 f16) against bank conflicts.
- The next phase's weight bytes and activations load into registers while the current phase computes and go to LDS after it; a schedule fence keeps those loads behind the current LDS stores.
- Epilogue kinds: `kstore`, `kqg` (q / gate split), `swiglu` (reads the f32 gate), `ffn` (gate and up fused), `kres` (residual add).
- afrag GEMMs (HAL suffix `.af`) read their input fragment-major, as the WMMA takes it (`norm_t`, or a producer's `.to` output form), instead of row-major.
- Segmented GEMMs (`seg_*`): small GEMMs that read the same input (alpha / beta, k / v) run as extra row tiles of the large one's dispatch.
- The 48-row alpha / beta use a 16-row x 64-token tile.

### Attention

`tools/gen_attn_fa.py`, FlashAttention-style with the softmax in registers. A workgroup is 32 query tokens x 2 query heads of one GQA group, 8 waves; each wave pair owns 16 queries and each wave one half of the head dim.

- S^T = K Q^T, so a lane owns one query column; the pair adds its partial scores through a private LDS slot.
- P^T becomes the B operand of the P.V WMMA through one xor-16 swizzle (`v_permlanex16`, HRX patch 0043). V is read as V^T tiles.
- The O rescale is skipped when no row max of the wave grew (exact).
- Workgroups run head-pair-fastest in longest-first order, so K/V tiles hit L2.
- Chunked prefill emits one attention HAL per chunk (`wmma_c<i>.hal`, start_pos = i B).
- Quantized KV: the attention reads the kv8 / kv4 codes directly, or f16 copies of the pools that `yah_kdeq*` / `yah_vdeq*` write in sets that carry them.

It is not bit-identical to a HIP-order kernel; the accuracy gate accepted it (build-and-run.md).

### Gated DeltaNet

`tools/gen_gdn_chunk.py`: the chunked WY form (chunk C = 32 tokens). A workgroup takes 64 value rows of one head, 8 waves; the state stays in f32 WMMA accumulators and the matmul inputs are f16. Gating is in log space; log2(alpha) is clamped at -100 because alpha underflows to 0 deep in the model. Output error vs the exact recurrence is ~2e-4 relative; end-to-end KLD ~3e-6.

### One HRX graph per chunk

`RunLayers` records a chunk's dispatches into one HRX graph (`LoomGraph` in `engine/model/loom_runtime.hpp`) and launches it once; layer 0 goes into a graph of its own first, so the GPU starts while the host records the rest. Edges come from the byte ranges each dispatch reads and writes (bindings a pair synchronizes through counters are left untracked). Kernels with no data between them run at the same time. Results are bit-identical to dispatching on the stream.

### Chunked prefill (long context)

A set emitted with `YAH_CTX=T` runs every kernel at the chunk size B but sizes the KV pools for T tokens. The prompt runs in passes of B tokens over the 64 layers, carrying the conv ring and the DeltaNet state between chunks. One-pass and chunked runs are bit-identical at 8K.

A prompt that ends inside a chunk runs a partial last chunk. The GEMMs launch only the token tiles that hold real tokens, and chunked sets carry each GEMM also with narrower token tiles (`LoomPrefill::PickGemm` takes the variant with the fewest padded token rows weighted by its cost per row); every other kernel runs the whole chunk over padding rows, which are zero-filled at allocation and so always finite. `yah_deltanet_prep_ab` and the DeltaNet read the real token count from a device scalar: padding tokens get decay 1 and update 0, so they leave the DeltaNet state unchanged, and the conv ring advances only past the real tokens. Attention is causal, so the real tokens never see the padding, and decode overwrites the padding's KV rows before reading them. The KV quantizers also read the real token count: `yah_kmean` averages K over the real rows only and `yah_vq8` / `yah_vq4` repeat the last real row into a partial 16-key tile. With quantized V, `yah_vseed` copies the real V rows of the last, partial 16-key tile into the decoder's open tile.

Slots: `SaveState` / `LoadState` write and read the sequence state after some chunks (KV pools, page table, conv rings, DeltaNet states) raw, for a prefill of the same set (`--slot-save` / `--slot-load` / `--slot-at` in `loom_forward_pp`): profiling at depth without re-running the prefix.

### NPU split

Each large prefill GEMM can be split by output columns: the NPU (XDNA2, 32 compute tiles through HRX `.xdna`) computes the trailing rows, the GPU the rest. A native UD-IQ4_XS set with the split (2.9 GB, ~170 s; needs numpy and gguf-py for the pre-decoded and transcoded rows):

```
YAH_NPU_FFNRES=0 YAH_NPU_FUSE=1 YAH_NPU_FFNBLK=8192 YAH_NPU_SPLIT=qkv=5120,gate=3072,q=6144,out=2560 \
  python3 tools/emit_prefill_pp.py <model.gguf> <dir> 2048
```

The NPU multiplies one-pass BFP16 (`bfp16ebs8`) operands with f32 accumulation. `tools/gen_npu_gemm.py` emits the NPU GEMM (array program + leaves, compiled by `loom-compile` with HRX patch 0013); `tools/npu_gemm_check.py` runs it through `iree-xdna-run` against a float64 oracle. A fragment is 8 rows x 8 consecutive k: per row `[E u8][8 x int8 m]`, value `m * 2^(E - 133)`, 72 bytes; E is the f32 exponent field of the block's max |x|. The NPU GEMM is a cascade: per column, 3 rows compute K-slice partials and pass them down the accumulator cascade, the 4th row adds its slice and holds C across passes (f32; on the last pass it packs each finished 16-row segment to bf16 in place, round to nearest even, and the C ring sends only that half: `LOOM_EXP_LS_SEND_PITCH=2` spaces the ring slots two records apart). A column computes 80 output columns (5 16-column weight slabs, `gen_npu_gemm.NP`) of 64-row M blocks: the kernel is bound by the operand streams into the tiles (36 * (1 / MP + 1 / NP) bytes per MMA over two ~7.7 B/cycle streams), and 5 slabs is the widest panel whose whole K = 5120 weights still fit a column's 512 KB memory tile; 8 columns make 640 output rows per call. A 5-pass call replays its weight panel in two pass groups (`gen_bfp16_encode.GROUPS`: every M block over passes 0-1, then over 2-4), each group a C partial that the unpack sums: while one group computes, the other group's memory-tile slots refill with the next call's weights, so calls stream back to back (Loom `LOOM_EXP_PANEL_GROUPS` / `LOOM_EXP_PANEL_STREAM`, `gen_npu_gemm.LOOM_ENV`; an image has five invocations: setup, a push on either descriptor set, a wait for the oldest queued call, and a lead push). The fills go out a few columns at a time so they do not take the DRAM fair share from the activation streams; the lead push, the first call of each job, issues them all at once, since nothing computes yet.

The GPU writes both operand streams in the NPU's layout (`tools/gen_bfp16_encode.py`): activations from the f16 GEMM input (`yah_bfp16_encode_act`; the norms that feed the K = 5120 sites write it themselves, `<norm>_bfp.hal` from `gen_half_norm.gen_split` bfp: 8 consecutive columns per lane, one row block each, staged in LDS and copied out as 36-byte runs, f16 output bit-identical, `tools/norm_bfp_check.py`; the DeltaNet postnorm over heads 0-39, ssm_out's NPU K chunk, too, `gen_postnorm_bfp` / `tools/postnorm_bfp_check.py`; the ffn unpack writes down's for its columns), weights straight from the quantized rows (`yah_dequant_<fmt>_bfp16`, `gen_gemm_tile.DQ_BFP`: the tile GEMM's dequant kind decodes each 64 x 64 phase into LDS as the GEMMs do, then every lane encodes row blocks (8 k of one row) into the phase's fragments staged in LDS, copied out as aligned 8-byte stores; one workgroup per (row group, K group)). The two-step form (`yah_dequant_<fmt>` f16 `[rows][K]`, then `yah_bfp16_encode_wgt`) is the checked reference. No weight copy persists. Both read K chunks of a longer row for the K = 17408 GEMMs, whose weight panel does not fit a memory tile (`DQ_BFP = (ks, passes, kb_start, kb_total)`; the encoder's `k_off` / `k_src`), and the encoder also reads the afrag GEMMs' fragment-major input (`tiled`). The kstore / kres / swiglu / fused-ffn / kqg split GEMMs (row-major and fragment-major output; kqg by whole heads, the unpack routing each NPU head's q and gate halves) and every encoder / decoder variant are checked byte for byte (`split_gemm_check.py`, `bfp16_check.py` with `BFP_SRC` / `BFP_KWIN`, `dq_bfp16_check.py` with `DQ_KCHUNK`). The GPU's share runs the kstore tile GEMM over the leading rows at the full output stride (`gen_gemm_tile.OSTRIDE`; `tools/split_gemm_check.py`, also in the prefill set's afrag form with f16 output for the DeltaNet qkv / gate: bit-identical rows for every format they use); `yah_npu_unpack` (`tools/gen_npu_unpack.py`, `tools/npu_unpack_check.py`) moves the NPU's bf16 C into the output's trailing columns (f32, or f16 rounded as the f16-output GEMMs round; for the other GEMM kinds also the kres residual add, the K chunks' partial sums, the swiglu `f16(silu(gate) * up)` with the GPU epilogue's ops, and fragment-major output), sweeping 4 output rows at a time across all column tiles (whole 128-byte lines read, 320 contiguous bytes stored per token and NPU column). `tools/bfp16_check.py` and `tools/dq_bfp16_check.py` check both against numpy oracles byte for byte, for every model format.

`engine/model/loom_npu.hpp` (`LoomNpu`) runs the NPU beside a `LoomDevice`: libamdf opens the XDNA device and the HRX xdna loader binds `.xdna` images. Shared operands are HRX device buffers, exported once as DMA-BUFs (`hsa_amd_portable_export_dmabuf` from HRX's own libhsa) and imported per binding view into the NPU, so GPU kernels touch them at full bandwidth; registered host pages work too, but they are snooped and cap GPU reads and writes at ~25 GB/s. It runs gated images (and the host-gated NPU attention, below): the host submits a chunk's jobs at once as fused commands (each job's calls with pushes one call ahead of the waits, because a command boundary inside a call's DMA work hung the NPU firmware under GPU DRAM load), the NPU waits for each job's ready word itself (below), and a reaper thread retires the commands. `engine/run/npu_split_run.cc`, driven by `tools/npu_split_check.py`, runs one split kstore GEMM as one graph the same way, on real weights and activations: the GPU's rows bit-identical to the full GEMM, the NPU's rows within half a bf16 ulp per partial of the BFP16 oracle.

In the driver (`--npu` with a set emitted with `YAH_NPU_SPLIT`; `emit_prefill_pp.npu_split`) every large GEMM of a full chunk can be split: the DeltaNet qkv and gate (one NPU job, the same activations), the attention q (kqg, whole heads; k / v run beside the NPU), ssm_out / attn_output (kres, K = 6144: the NPU takes K 0 - 5119), the FFN gate + up (the fused ffn or kstore + swiglu: the NPU computes the same rows of both, the unpack applies silu(gate) * up) and ffn_down (kres, K = 17408: the NPU takes three chunks of 5120). The NPU runs one image, K = 5120 per call (switching images costs ~0.55 ms each, 4 per layer before): the rest of out's and down's K (1024 / 2048) for the NPU's rows runs on the GPU beside the GPU's rows (`npurem_<site>_<fmt>.hal`, `gen_gemm_tile.KWIN`, f32 [tokens][rows]) and the unpack sums the chunks, that partial and the residual. Per site: the activation encoder writes the GEMM input (row-major or fragment-major, whichever the GPU GEMM reads) into the shared A, the NPU's rows are decoded straight into W panels, the NPU calls (one per 640 rows and K chunk) are handed over (`NpuEnqueue`); the GPU's rows run beside them (`<hal>.npu.hal`: every form of the set's GEMM, OSTRIDE); then `NpuJoin` and `yah_npu_unpack`. The DeltaNet qkv site has no full unpack: the conv reads the NPU's v channels straight from C (`convkq_c.hal`, `gen_conv_kq.gen_c`: lanes take the unpack's work items, sum and round them with its ops into LDS, then one channel per lane; bit-identical) and the GPU's channels from the f16 output (`convkq_g.hal`, `gen_conv_kq.gen` climit); `npu_unpack_qkv_tail.hal` writes only the last 8 tokens, the conv ring `prep_ab` reads. A chunk, NPU handoffs included, is one HRX graph: a handoff is a pair of 32-bit words in host memory (`NpuSplit::Flags`). At `NpuEnqueue` the graph stores the job's gate value to its ready word with an atomic-store node (HRX patch 0015, release + system scope: the command processor writes the encoders' and decoders' output back to memory before the word); the NPU waits for the word itself (below) and writes the value to the job's done word. At `NpuJoin` `yah_npu_flag_wait` (`gen_npu_unpack.gen_flag_wait`, one wave, system-scope acquire loads) polls the done word; in the graph's dependencies it stands for the NPU's reads of A / W and writes of C, so the unpacks and the next job's encoders order after it. The wait is bounded (~2 s, then it sets a status word that `NpuSplit::Enqueue` and `Report` check); the status is sticky, so once one wait failed every later one returns at once, and the host stores the done word with `kGateFailed` for a failed NPU command, so a lost NPU job cannot hang the GPU. From the done word to the GPU continuing takes ~8 us. Without the NPU the graph has no handoffs (bit-identical). `NpuSplit` (`engine/model/npu_split.hpp`) keeps libamdf out of `LoomPrefill`; `LoomNpuSplit` (`loom_npu.hpp`) binds one kernel instance per (image, A / W / C views), and `EnableNpu` binds all of a chunk's calls up front with a pass of the layers that dispatches nothing (a cold bind loads and patches the image's storage, ~3 ms each; `EndBinding` then frees the instances' storage, since the calls and setups are host copies, hardware.md). A job's weight decode runs beside the previous job's GPU work while the NPU works (W has two slots): the planning pass in `EnableNpu` records each job's decodes, and the previous job's `NpuJoin` dispatches them before its wait (`NpuDecode` dispatches one itself where the plan differs, the last layer's trimmed tail). The split out / down GEMMs have fewer row blocks than the 40 CUs: the persistent kres takes the first three token tiles and the tiled kres the last one beside it. C, which the NPU writes, is in host pages registered with libamdf and imported into HRX (`LoomNpu::CreateShared` host). Fabric / memory clock switching during NPU work raises deferred data-fabric machine checks that can corrupt an NPU output: run NPU work with the GPU performance level pinned high (results.md). Calibration is off for NPU chunks. C lives in host pages, which the GPU does not keep in L2 between kernels (a probe read host data a kernel had cached a moment before and saw the new data 100 times of 100), so the unpacks need no acquire. Fused sets (`YAH_NPU_FUSE`) call 512 rows at a time and give each site image its own family: a change of image runs that image's setup at a job boundary (a decoder-column swap would splice a whole fused image's first call into the job, which stalls the array), so a DeltaNet layer whose qkv and gate formats differ runs them as two jobs; a site call's raw rows reach its fillers over the core stream (the W-DMA raw ring of the FFN block's images hangs plain-activation calls).

No host relay sits between the GPU and the NPU (HRX patch 0016): the NPU image waits for each job's ready word itself. `LoomNpuSplit` queues a chunk's jobs right after the graph launches, up to 16 jobs (256 calls; 8 jobs in decoder-column sets, whose layers without NPU work leave longer waits) per NPU command, so a pp2048 chunk is 16 commands, the longest ~120 ms against the driver's 2000 ms command limit; a reaper thread retires the commands in order. A command is the jobs' control code spliced under one transaction header (libamdf's public format 0.1). In the image (`gen_npu_gemm` GATE) column 0's head core is the waiter. After its last firing of a job it polls the job's 16-byte flag record request-driven: each poll is one tick on the core's own stream output (a shim S2MM releases a shim lock) and one flag read on its stream input (the shim MM2S acquires the lock first). Even so a poll sees ready ~17 polls after the GPU stored it (pp2048, fitted from the polls per job against the idle before it), so a wait costs ~17 poll intervals. It waits until ready >= (its job count + 1) * 64 (`GATE_CALLS`) at a constant ~0.31 ms per poll for 896 polls (~280 ms, the longest gap between FFN block layers) and backs off over the last 128, so the supply of 1024 polls lasts ~1.3 s (the tick stream takes one record per poll, and 1024 is the most the shim's descriptors chain). Backing off from the start cost each job 4-17 ms, growing with the idle gap before it (pp2048 ~-90 ms with the constant pace). It then hands the ready value to its neighbor mid over a leaf-synchronized neighbor channel, and the mid emits go and done on its stream output. The control program's gate invocation waits for go before any of the job's data moves; its done invocation queues done after the job's last C write, so done lands after C. The ready value is the job's sequence * 64 + its call count (`NpuSplit::NewJob`): ready and done live in per-call gate slots (the job's first and last call), and jobs of different sites share slots, so the count travels in the value. The set carries the protocol (`npugate <supply> <calls> <record>` in dispatch.txt, from `gen_npu_gemm.GATE_*`). `yah_npu_flag_wait` waits until done reaches the ready value; bit 31 in done (`kGateFailed`) means the NPU gave up, and the host sets it for a failed command, so no GPU wait spins on a lost job. The head's job state lives in private storage that the array setup zeroes, and the image's ungated setup call runs once before the first gated job; in decoder-column sets (`npugfirst`, `gen_npu_gemm` gfirst) the waiter and the mid wait at a job's first firing instead, so zeroed state is at the gate and the setup runs no call.

NPU FFN block (`YAH_NPU_FFNBLK=7168`, decoder-column sets, `RunFfnBlock`): the NPU owns the last 7168 features of the FFN in every layer whose gate and up share an IQ4_XS / IQ3_S / IQ3_XXS format (up stored right after gate) and whose down is IQ3_S / IQ3_XXS / IQ4_XS / Q4_K (36 of 64 layers; 63 with the column pairs below; the last layer's FFN runs only the kept rows' token tiles, never the block). Only the norm's output goes in and one residual delta comes out; the NPU reads raw GGUF rows and chains its own results. Three jobs per layer, each one image family:
- gate / up + swiglu (`npu_ffnsw_<fmt>`, 32 calls, `gen_npu_gemm` swsplit, 4 slabs per column): call j's column c takes features 8 (128 c + 4 j) + [0, 32). Its raw stream per pass is the 32 gate rows, then the same up rows one gate tensor further (a shim descriptor chain, HRX patch 0019); slabs 0-1 are gate, 2-3 up. The tail applies silu(g) u (2^n exact, 2^r by a cubic, 1 / (1 + e) by two Newton steps; ~0.3% of a block's max, at most 2.6%) and writes bfp16 fragments into H in C: [64-token block][pass 7][16-token slab][128 k-blocks], so column c writes pass c and down reads each record without a descriptor chain. The image runs one replay group, so the norm before it writes its activations in that group's stream layout (`norm_t_bfp_g1.hal`; the layout depends on the groups): no encoder runs for the block.
- down (`npu_ffndn4_<fmt>` / `npu_ffndn3_<fmt>`, passes 0-3 and 4-6 of the 7168 features, 10 calls of 560 rows, the last at rows 4560-5119 overlapping the 9th): activations from H (`ain "h"`), grid decoders in natural k-block order (`gord "N"`), each part a bf16 partial after H.
- H's k-block order is the down decoder's: natural for the grid decoders (`gord "N"`); IQ4_XS decodes in P4 order ((0, 2, 1, 3) per 4 k-blocks), Q4_K in (0, 4, 1, 5, 2, 6, 3, 7) per 8, so their layers' gate / up images (`_p4` / `_q4k`, `gen_npu_gemm` hord, their own image families) write H in it. Positions stay in the tail's loop order over (slab, 8-row half); P4 visits slab (j & ~1) | i, half j & 1. Q4_K's order spans 8 k-blocks and a same-format call computes 4: its two gate slabs are 32 rows apart (the raw view's slab step; call j's rows from 64 (j / 2) + 16 (j % 2)) and the tail visits them as P4; column pairs (8 k-blocks per call) visit slab (j >> 1) + 2 i, half j & 1.
- The GPU runs the other 10240 features (the fused ffn's split, `<hal>.af.to.npu.hal`) and down over them (`npuffnrem_<fmt>.hal`, a leading K window, f32), then `npu_unpack_ffnblk.hal` writes hidden + that + both partials.
- Layers whose gate and up formats differ (27 more: IQ3_S / IQ3_XXS, IQ3_S / IQ4_XS, IQ4_XS / IQ3_S, Q3_K / IQ3_S, IQ2_XXS / IQ3_XXS, IQ3_XXS / IQ2_XXS, IQ2_XS / IQ3_XXS) run column pairs (`npu_ffnsp_<gate>_<up>`, `gen_npu_gemm` ufmt, F = 6144, 32 calls of 192 features): GEMM columns 0-2 compute gate rows, 3-5 the same features' up rows, each fill worker decodes one format (raw gate and up rows are two bindings, `BindRawPair`). Each gate tail packs its C segment to bf16 and sends it over a core-to-core stream (HRX patch 0019: worker-to-worker core stream channels) to its up tail, which applies the swiglu and writes passes 2 u and 2 u + 1 of H; the gate tails' own C records go to scratch. The fill workers sit in column 7 like every other image of the set, column 6 stays unused (hardware.md: a tile that changes between fill and GEMM roles across images stalls the later image). Down is two dn3 parts (passes 0-2, 3-5); the GPU's side is the kstore / swiglu split pair at 11264 features.

An image's setup writes only the state it uses, so images of other layouts sharing the context set `LOOM_EXP_ROUTE_RESET` (every non-swap decoder-column image): before its routes the setup disables every data master of the stream switches in its columns, clears the shims' packet rules and resets every memory-tile DMA channel there. A command switches image families at job boundaries: it runs the job's image setup and one ungated call (a copy of the image's first command taken at load with its C bound to scratch, not a second instance: the NPU's command memory holds ~90 instances), because a gated head expects that call before its first job. With `npugfirst` the copy is the setup alone (Loom `LOOM_EXP_SETUP_ONLY`): ~0.4 ms less per switch, pp2048 -68 ms. The gate counts jobs from 1 after each setup (`NewJob` per family run); every chunk starts with a setup, and the graph clears each job's ready and done words once it joined the job (`NpuJoin`), so the next chunk reuses them with no host step between chunks. Setups are spliced as deltas (`LoomNpu::DeltaSetup`): the host models every core tile's program memory as the commands built so far leave it and writes only the program words that differ (runs less than 32 words apart as one write: a write op costs about as much as ~150 bytes), and drops a read-only data block (decoder tables) when the last setup that wrote that tile wrote the same block; zero-filled storages, registers and DMA waits always run in full (pp2048: 117 -> 64 MB of commands, bit-identical results). Loom puts every core program at the top of program memory (HRX patch 0029), so images that share a code tail hold it at the same addresses (pp2048 setup program bytes 110 -> 82 MB). A failed command or a setup outside FusedCommand forgets the model. Commands still run to several MB and the NPU's command memory is small (hardware.md): command arenas are a ring, reused once their commands retired, and the driver's queue depth paces the host's submissions through the chunk. A chunk's commands depend only on its jobs and the program state it starts from, and a chunk leaves every word its setups write as they set it: once two chunks in a row queue the same jobs (with no forgotten state since), the second records its commands into their own command storage (`LoomNpu::Script`) and later such chunks resubmit them unbuilt (fx0, 4 chunks of 2048: 87 -> 44 MB built, bit-identical).


Token halves (`LoomPrefill::RunDeltaNetHalves` / `RunAttentionHalves`, decoder-column sets with a `h/` directory): in a full chunk a layer's qkv / gate or q job and its out job run per half of the chunk's tokens, so the NPU computes half 1 while the GPU runs half 0's DeltaNet or attention chain (with whole-chunk jobs the NPU idled ~5 ms per layer, most of it during those chains). GPU order per layer: per half the FFN block's unpack of the previous layer and the attn norm (each queues its half's job), the GPU's qkv / q rows for the whole chunk, per half the chain (unpacks, conv, DeltaNet, or RoPE and attention), its out job and the GPU's out rows, then per half out's unpack and the FFN block's norm. Half h runs the kernels of `h/` (the set emitted at half the chunk, `emit_prefill_pp` writes it along) on token views from h * B / 2 (fragment-major layouts are 16-token tiles); half 1 continues the conv ring, the DeltaNet state and the paged KV like a next chunk (attention half h is that set's chunk 2 ci + h). NPU images have M compiled in, so the sites run `h/`'s 1024-token images (9 more image families). The FFN block stays whole: `npu_unpack_ffnblk_h<i>` and `norm_t_bfp_g1(s)_h<i>` cover half i's tokens of its whole-chunk C and stream. When qkv and gate need different images (formats), gate runs as one whole-chunk job between qkv's halves (the whole set's image, its own A stream in out's half-1 slots, C past half 0's region): one image switch and one panel decode less than its two half jobs. Each half job has its own A slot and C region (`HalfA`, `HalfC`): no GPU kernel reads a job's C range between its ready store and its join (the graph orders a read only after the store), and no GPU kernel writes an A range the NPU still reads. `NpuEnqueue` takes the job's A / C ranges, `NpuJoin(job)` waits for one job and clears only the flag words of the jobs it joined. The results are bit-identical to the whole-chunk path.

### NPU attention

For splitting prefill attention with the NPU: `tools/gen_npu_attn.py <out.loom> <mc> <nb> [out.xdna]` emits a one-pass bfp16 attention over 2 mc compute tiles (mc <= 16 pairs), each holding 16 query rows of one KV head, with the K / V records streamed to all of them. A body is one 32-key K record: a QK round (S = Q K^T + C in f32 chains from row constants C, a Cauchy-Schwarz bound that keeps U = S + C in the core exp's range without a max pass), the softmax of the previous body's S (P = 2^(U - 128) in one accumulator, pushed as bfp16), and one 64-step P.V round over the P of the 16 bodies before; row sums l ride as an MMA chain. 512 MMAs a body; the GPU takes the first 32 keys (the sink: its large S makes bfp16 Q's rounding the largest error there), the keys after the NPU's and the diagonal, and combines O / l.

- Each core of a pair receives half of every record and reads the other half from its partner's tile; a token channel keeps the pair in step.
- Each of the 4 streams sends the call's payloads (bindings 4 + mc ..: each core's Q, C and park starts, plus a zero record when mc is even) and then the KV head's records (bindings 0 - 3), which every call of the head shares. The shim reads them as two chained descriptors: HRX patch 0068's `constrain.prefix` binds the first records of a channel to their own binding.
- Layout and order come from Loom planner switches (`gen_npu_attn.LOOM_ENV`: pinned ring records, the bank map `npu_attn_banks.txt`, HRX patches 0059-0067) and from `npu_attn_sched.py`, a cycle model whose issue order is the emission order of the locked leaves.
- The cores read nb from the payload, so an image built for nb runs any smaller even nb: `gen_npu_attn.patch_nb` rewrites the 4 record descriptors' lengths (the host does the same in each call's invocation bytes).
- Calls chain as control-only continuations (no tile setup): every ring holds an even number of records a call (V ends with a dummy), so each ring ends a call where the next starts, and the upper core of a pair returns at its end the token credit that the lower core's first acquire takes (setup puts one in). A chained call costs ~111K cycles on top of its bodies with the host submitting and waiting per call (a fresh call ~1 ms).
- The engine runs it through `LoomNpu` (`LoadAttn`, `BindAttn`, `EnqueueAttn`), host-gated: no core is free to wait for the GPU. `BindAttn` copies a call's invocation bytes as bound to its views (records, outputs, payloads), the first invocation (setup and one call, 514 KB at mc 16) and the continuation (2.4 KB). `EnqueueAttn` builds a layer's calls into one command (the first call's setup only when another image ran since, nb patched into each call's 4 record lengths) and queues it; the submitter thread polls the job's ready word (~20 us apart), submits, and the reaper stores the done word once the command retired. Any failure, or a ready word still missing once the GPU has finished (`Drain(true)`, after the host's last sync), fails every queued attention job (done | kGateFailed). There is no time limit: the host queues chunks seconds ahead of the GPU. Gated GEMM jobs may not queue behind an unsubmitted attention command (`EnqueueGated` throws): the image needs Loom's route reset before it can share a chunk with the GEMM images. Calls in one command start ~63K cycles apart beyond their bodies (vs 111K for one submission a call): 2% of a call at nb 4000, 57% at nb 64.
- `engine/run/npu_attn_run` (`npu_attn_check.py --runner CALLS,JOBS`) runs jobs of chained calls this way, every call with its own payload copy and outputs, the ready words stored by a GPU graph; with `<passes> <ref_dir>` it soaks them against a fresh call's outputs as the GPU reads them.
- The GPU's side is the 2 x 64 key-split pair's NPU twins (emit `YAH_NPU_ATTN=n` with `YAH_ATTN_KSPLIT`: `yah_attn_hip64ksn` / `kmn`, gen_attn_fa `NPU_KV`): the last n KV heads' units go to the NPU over keys [32, k_lo), k_lo = 512 floor(start_pos / 512) (an image built for nb = 16 (floor(start_pos / 512) + 1)), so they need start_pos >= 512. Kernel 1 runs one piece of each over [k_lo, end) after the tail pieces and stores its partial; kernel 2 runs the sink [0, 32) and merges the three per row and head (m = 128 - C for the NPU's, its l = the l block x 2^63), streaming each merged fragment over kernel 1's record (16 fragments live across the join spilled). On chunk 63 of a 128K dump (from the removed MQ4 A4 path; to redo on UD-IQ4_XS) with a float64 stand-in for the NPU's piece (`Scratch/npu/attn/merge/gate.py`), heads 0-17 match the plain pair to 3e-6 mean, the NPU's heads stay within the plain pair's error to float64, and kernel 1 takes 150 ms vs 194 (one KV head of four).
- Prefill: a set emitted with `YAH_NPU_ATTN=n` (fp16 KV, or kv8 through its per-layer f16 copies `yah_kdeq8` / `yah_vdeq8`, not KRAW) runs the twins from chunk `YAH_NPU_ATTN_FROM` (default the first key-split chunk) and adds per chunk the encoders `npua{k,v,q}_c<c>.hal`, the GPU's wait `npu_flag_wait.hal`, the image `npu_attn.xdna` (built for the last chunk's nb) and the dispatch.txt row `npuattn <n> <nb built> <first chunk>`. `loom_forward_pp --npu` hands `LoomPrefill::EnableNpuAttn` a `LoomNpuAttn`. Each attention layer of an NPU chunk then runs the encoders on the attention's own q and K / V pools, stores its ready word (release, system scope), runs kernel 1 while the NPU computes, waits for the done word (`npu_flag_wait`: ~2 s, then the sticky status word) and runs kernel 2 on the NPU's outputs; the chunk's jobs are queued once its graph is launched. A chunk whose rows nobody reads skips the last layer's attention (15 jobs). Unlike the GEMM split it runs on the auto DPM level (results.md).
- `tools/npu_attn_check.py <dir> <mc> <nb> [--real <dump> | --inputs <npz>]` runs it through `iree-xdna-run` against a CPU emulation of the core arithmetic (O and l bit for bit) and, on real data, against float64. Its docstring has the record formats.
- The GPU writes the streams in place (`tools/gen_npu_attn_encode.py k|v|q`): K records from the paged f16 K pool (and each record's max squared key norm), V records from the paged V^T tiles, and each call's payloads (its own pair of buffers) from the attention's split-norm query (gen_attn_fa `R2P_QSPLIT`: the f16 halves, the rotary dims RoPE'd op for op as the attention does, scaled by r log2(e) / 16) with C from the norms. A record depends only on its own keys, so earlier records stay valid in later chunks. For prefill the encoders also take the image's record stride (`nbs`: its stream views are fixed, a chunk's nb is patched in), layer forms (`kvn`: the records and every call's payloads of the last kvn KV heads, one dispatch each) and the raw f16 query of sets without split-norm Q (`qlay=1`: the encoder does the head norm and RoPE as the attention does, then f16(x / 16)). `tools/npu_attn_encode_check.py <dump> <dir> ...` checks them on the GPU (K / V bit for bit against `npu_attn_check.encode`, the payloads against float64, the pool pages shuffled) and writes the `--inputs` file for the NPU run.

2026-11-13: bit-exact at mc 1 (nb 48) and 16 (nb 64, and the nb 64 image patched to 48), 730-731 cycles a body on every core (70% of one MMA a cycle); real dump (k8_c63_l8, 992 keys at depth 128K, from the removed MQ4 A4 path): mean |err| 1.4e-3 vs float64, max 1.6e-2. On the GPU encoder's bytes (keys 32 ..): bit-exact, mean |err| 1.3-1.6e-3, max 1.8-2.6e-2 (keys 0 .. instead: max 0.38, the sink). The encoders at nb 4000 (127K keys, one KV head): K 1.68 ms, V 0.65 ms, payloads 0.013 ms. 101 chained calls on all 32 cores (nb 48): the last call's O and l equal a fresh call's. Through `LoomNpu` (mc 16, image built for nb 480): 4 jobs x 24 calls at nb 64 and 3 x 8 at nb 480 bit-exact against the emulation; soaks of 300 passes x 4 x 24 calls (nb 64) and 200 x 3 x 8 (nb 480) equal to a fresh call in every call.

## Engine

`engine/model/engine.hpp` (`Engine`) loads the model, a chunked prefill set and a decode set once and serves `Generate(prompt, params, on_token)` calls one at a time (the `TextGenerator` interface in `engine/model/generator.hpp`; the server in `engine/serve/` talks only to that). Per request: reset the recurrent state, prefill the whole chunks, finish the tail with a partial chunk or with decode steps (whichever its measured costs say is cheaper), then decode. Greedy takes the argmax on the GPU; temperature / top_p sample on the GPU too (`gen_sample`). With the NPU (`--npu`, `LoomNpuSplit` in `engine/model/loom_npu.hpp`), a prefill set emitted with the NPU split runs it (NPU split, above).

## Decode

`engine/model/loom_decoder.hpp` (`LoomDecoder`) is the single-token step. `loom_decode` feeds a prompt through it one token at a time; `loom_forward_pp --gen` runs it after a prefill, on the prefill's KV pools and recurrent state. Decode reads every weight tensor once per token (one embedding row), so it is a bandwidth problem (results.md, Decode floor).

### Step, per layer

1. `rmsnorm` (attn_norm).
2. Input projections as one band-fused GEMV (`gb_*`): attn_q / attn_k / attn_v, or attn_qkv / attn_gate / ssm_alpha / ssm_beta, in one dispatch.
3. Full attention: `unpack` (q / gate), `rope` (QK norm + RoPE), KV append (`dattn_kvappend`, or `dattn_kappend_q` + `dattn_vappend_q`), `dattn_part` (or `dattn_part_q`), `dattn_reduce`, then `gv_resid` attn_output.
4. DeltaNet: `deltanet_conv` (the conv fused into the DeltaNet step, gated norm inside), then `gv_resid` ssm_out.
5. `rmsnorm` (post_attention_norm), `gv_swiglu` (ffn_gate and ffn_up in one kernel), `gv_resid` ffn_down.

Head: `rmsnorm` (output_norm), `gv_plain` output (248320 rows) with the argmax in it. The argmax writes the next token id into a device token stream; the next step's `embed` kernel (Q8_0 row) reads it. Positions come from a device array. So steps are enqueued back to back and the host waits only after the prompt and at the end. Each step is submitted as soon as it is recorded (`LoomDevice::Flush`), so the GPU runs one step while the host records the next.

### Flag-chained dispatch

A stream dispatch ends with an ordering barrier: the next kernel cannot launch until the previous one has drained (~4 us per boundary). With decode.txt `chain` (the default, `tools/gen_chain.py`) every decode kernel instead waits on its producer's counter:

- `gen_chain.chain` adds a counter buffer and three i32 push constants (wait slot, target count, own slot) to a 1-D kernel. Wave 0 polls the wait slot (acquire, device scope) until `(count - target) >= 0` as i32, then a workgroup barrier releases the other waves. At the end, lane 0 of every wave adds 1 to its own slot (release, device scope).
- The host (`LoomDevice::ChainDispatch`) keeps a shadow of the 1024 monotonic counters: each dispatch waits on the previous dispatch's slot for its full count (workgroups x waves) and signals the next slot. Slot 0 is never signaled. kvappend and vappend share one slot (join): they write disjoint caches.
- Workgroups launch in order, so a waiting workgroup never blocks its producer. Every dispatch waits on the one before it, so the order is still linear (no write-after-read hazards).
- Any other stream op (copies, fills, graph launches) records the ordering barrier first (`LoomDevice::Order`).

Logits are byte-identical to the barriered step. On top of the chain:

- Peeled GEMV start (`emit_decode.PEEL`, `gen_gemv` peel): a chained GEMV runs its first K iteration before the loop, split by dataflow at a `// chain.wait` marker. The weight loads and their decode, which do not read x, issue before the wait, so the first weights arrive during the producer's tail. Band GEMVs have one marker per band branch.
- DeltaNet state stores (decode.txt `latestate`): `deltanet_conv` stores its updated state after its output, past a `// chain.signal` marker, with gfx11 DLC (no MALL allocation, HRX patch 0045), so the 3 MiB per layer do not get flushed out of the MALL during the next GEMV's weight stream. `LoomDecoder::Step` starts each step with `Order()`: the next token's DeltaNet reads the state after it.
- Greedy argmax in the output GEMV (decode.txt `amax`, `gen_gemv.amax_tail`): each workgroup reduces its rows' keys (order-preserving bits of the logit, then the inverted row, as a u64; NaN and +-inf skipped, -0 as +0) through LDS and takes one atomic max; the last workgroup by count stores the row as the token and resets the key. Ties keep the lowest index. Sampled steps run the output GEMV without it and then `gen_sample`.

### GEMV design

`tools/gen_gemv.py`, one kernel per (kind, formats, rows, K), in the GGUF's own formats: Q8_0, Q2_K-Q6_K, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_NL and IQ4_XS, the IQ grids bound after the weights; token_embd is Q8_0 (converted at load).

- Decode on 32-bit words (`vector<4xi32>`), never on `vector<16xi8>`, which Loom lowers byte by byte.
- Two rows per wave share each x load; 4 waves per workgroup (R x W = 2 x 4, decode.txt `rw`).
- `pipeline(2)` read-ahead on the block loop; butterfly reduce over the wave.
- Kinds: `plain`, `resid` (y += W x, the residual add fused), `swiglu` (gate and up in one kernel), and bands (`gen_bands`, several output matrices of one input in one dispatch).

The GEMVs streamed at ~237.6 GB/s of the 240 GB/s peak (measured on the removed MQ4 GEMVs, 2026-10-20; not re-measured on the GGUF formats).

### Decode attention

`tools/gen_decode_attn.py`, split-K over pages:

- `part`: one workgroup per (KV head, 256-key page), with the six query heads of the GQA group. Scores (thread = key), per-head block max and sum, p in LDS, then P.V (thread = dim). Read-ahead depth 3 on the K rows and 2 on the V^T tiles. Grid order (head, page) so the four KV heads of a page read together.
- The last page is partial (keys up to `pos` only). Waves whose 32 keys are all past `pos` skip the scores loop, and P.V runs tiles 8-15 only when a visible key is there. Both guards sit outside the pipelined loops: a branch inside one makes every join wait for all loads (`vmcnt(0)`). The output is bit-identical. `part_q` sits at 256 VGPRs and spills with either guard, so it runs every key.
- `reduce`: one workgroup per query head, merges the pages and applies the sigmoid gate.
- Quantized KV (`part_q`): same grid and outputs, the reduce is shared. q goes to LDS in the codes' storage order (kv4: rotated in place by an 8-stage LDS butterfly). Each key thread dequantizes its own row. The open f16 V tile is added once after the tile loop. The K channel mean is never added back: q.m is constant over keys and cancels in the softmax.

## Data layouts

### Paged KV

All KV caches are paged with 256-token pages. One page table per sequence (i32, logical page -> physical page) is shared by all layers. A 16-key attention tile always lies in one page, so attention does one page-table load per K tile and per V tile. The host validates every entry (< number of pages) before upload; attention assumes the bound, the cache writers clamp to it. The context must be a multiple of 256.

Per full-attention layer, at context T (pool rows = T):

| format | K | V | bytes per token per layer |
|---|---|---|---:|
| fp16 | `[T][1024]` f16, row of position p = `ptab[p/256]*256 + p%256` | V^T `[4 kv heads][T/16 tiles][256 dims][16 keys]` f16, physical tile `ptab[t/16]*16 + t%16` | 4096 |
| kv8a16 | int8, one scale per (token, KV head, 128-dim half): codes `[T][1024 B]`, scales `[T][8]` f16 pairs | uint8 per channel per 16-key tile around the tile midrange: codes `[4][tiles][256] x 16 B`, stats `[4][tiles][256]` f16 pairs | 2336 |
| kv4a16 | H256 (Walsh-Hadamard over the whole head) of K, asymmetric int4 per 32-dim group: codes `[T][512 B]`, scales `[T][32]` f16 pairs | 15 levels per channel per 16-key tile: codes `[4][tiles][256] x 8 B`, stats as kv8 | 1408 |

Over 16 layers that is 64 KiB (fp16), 36.5 KiB (kv8a16) and 22 KiB (kv4a16) per token of context; at 32K context 2.0 / 1.14 / 0.69 GiB.

Details of the quantized formats (`tools/gen_kvq.py`):

- K is centred first: `yah_kmean` computes the per-channel mean of the first chunk's K (deterministic, no atomics), kept per layer. Subtracting a per-channel constant shifts each query row's scores uniformly, so softmax is unchanged.
- kv4 rotates K with H256; the attention rotates q the same way, so q.k is unchanged.
- Codes are stored in an order that lets the attention build f16 values with masks and ORs (`1 + u/16`, `1 + u/256`), then dequantize with one fma `f * S + C'`. All attention math stays f16 WMMA ("a16").
- With K and V quantized, the f16 KV cache is a one-layer, one-chunk scratch that RoPE writes and the quantizers read.
- Decode keeps each layer's open 16-key V tile in f16 and quantizes it when the 16th key arrives. Prefill runs end on whole chunks, so a handoff always starts on a tile boundary.

### Recurrent state

| buffer | layout |
|---|---|
| conv state | `[48 layers][10240 channels][4]` f32. Decode ping-pongs between two copies per token, so the three value heads that share a key head never read a half-updated state. |
| DeltaNet state | `[48 layers][48 value heads][128][128]` f32 (3 MiB per layer) |

Prefill and decode use the same layouts, so the decoder binds the prefill's buffers directly.

## HAL sets

A HAL set is a directory of compiled kernels plus one text file that records how to launch them. The drivers read the file and refuse any other grid: Loom drops index clamps it proves redundant from the launch grid, so a larger grid reads out of bounds (see build-and-run.md, GPU safety).

### Prefill set: `tools/emit_prefill_pp.py <model> <dir> [B]`

- One GEMM HAL per (kind, formats, shape, input form), the fixed kernels (`embed.hal`, `norm*.hal`, `convkq*.hal`, `rowsplit*.hal` = DeltaNet, `postnorm*.hal`, `prepab*.hal`, `rope.hal`, `wmma.hal` = attention, `rmsnorm.hal`, `gemv.hal`, `argmax.hal`, ...), one rope / attention / KV-writer HAL per chunk, and the IQ grid tables.
- `dispatch.txt`, one line per HAL: `<hal> <tokens per workgroup> <row groups> <token tiles>`. Marker rows with zeros carry the set's features (`native`, `kv_paged`, `qsplit`, `gsig`, `dnsplit`, `ctx <B> 0 <T>` for chunked sets, ...). The driver refuses a set without `native` (a set of the removed MQ4 path).
- `tools/footprint_gate.py` runs for every GEMM before it is emitted and refuses a kernel whose declared operand footprint is larger than the buffer the driver binds.

### Decode set: `tools/emit_decode.py <model> <dir> [max_context]`

- `gv_<kind>_<fmts>_<M>_<K>.hal` and `gb_<fmts>_<Ms>_<K>.hal` (GEMVs and band GEMVs), `dattn_*` (attention), `rmsnorm`, `unpack`, `rope`, `deltanet_conv`, `embed`, `argmax`, `sample`, `penalty`, and the IQ grid tables.
- `decode.txt`: `ctx <T>`, `kv q <K bits> <V bits>` for quantized KV, `chain` (flag-chained kernels; sets without it run barriered), `amax` (argmax in the output GEMV), `latestate`, `rw <kind> <R> <W>` (GEMV geometry), and `grid <hal> <workgroups> 0` for every GEMV kernel.
- To decode after a prefill, emit the decode set with the same context as the prefill pools and the same `YAH_KV`. The driver refuses a mismatch.

### From generator to HAL

1. A generator (`tools/gen_*.py`) prints Loom text, one kernel per `gen_*` function. A few kernels are still hand-written `.loom` files in `engine/gpu/loom/`; the emitters compile those with fixed configs.
2. `engine/gpu/loom/emit_hal.py <file.loom> <outdir> sym=value ...` replaces every `config.get` with its constant, drops the `config.decl`, and has `iree-run-loom --emit-only --emit-hal-executable` compile the kernel for gfx1151. The kernel is built for exactly that config. The HRX/Loom tree is `external/hrx` (`engine/gpu/loom/hrx_paths.py`; `YAH_LOOM_HOME` points it elsewhere for diagnosis).
3. The emitter copies the result into the set and writes `dispatch.txt` or `decode.txt`.

Production sets build with the pinned HRX/Loom plus `engine/hrx/patches` (see build-and-run.md, HRX patches). Any other compiler change is for diagnosis only until it is a patch there.
