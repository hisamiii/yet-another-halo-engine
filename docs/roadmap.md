# Roadmap

What is next, and what is planned but not built. Numbers behind the leads are in [results.md](results.md).

## Next: user-facing

- Speculative decoding on the GGUF sets: the MTP drafter and the 4-token verify GEMVs went with the MQ4 path (2026-11-14; be687da has them). The GGUF formats need their own T-token verify GEMVs, then the MTP layer (`blk.64.nextn.*`) as the drafter, greedy first, then rejection sampling for sampled requests.
- One-command setup: fetch the ROCm runtime and HRX, build, emit the default sets and download the model in one script, with clear errors for a missing piece.

## Then

- Vision: the projector (`mmproj-F16.gguf`, 0.86 GiB) and image tokens (64-16384 per image) merged after it. Gate: an image prompt gives correct output.
- Stronger drafters than the MTP layer, both published for this model (looked at 2026-10-26):
  - EAGLE-4 (`EAGLE-Corp/Qwen3.8-27B-EAGLE4`, 6.2 GB BF16): one Llama layer (hidden 5120, 40 heads x 128, MHA, FFN 16384, sliding window 4096) over the target's hidden states of layers 3, 31 and 59, and a rank-128 low-rank head that scores 128 candidates. Needs: capturing those hidden states in the verify and the prefill, a 40 x 128 attention (ours is built for 24 / 4 x 256), the drafter's weights in a format the kernels run, and tree drafts (a tree verify: a mask over the T tokens in the attention kernels).
  - DFlash 2 (`z-lab/Qwen3.8-27B-DFlash2`): a block diffusion drafter, 5 non-causal Qwen3 layers (32 / 8 heads x 128, FFN 17408, window 2048) that fill a block of 8 mask tokens in one pass from the target's hidden states of layers 5, 19, 33, 47 and 61. Needs the same hidden-state capture and weight conversion, a non-causal attention for its geometry, and verify of 8 drafts (wider T-token GEMVs).
  - Both pay only if the verify is cheap: the MQ4-era verify of 4 drafts cost 1.45 steps (results.md), and their longer accepted runs need wider verifies.

## Performance leads

- Prefill, partial chunks: only the GEMMs shrink to the real tokens; the norms and other small kernels still run the whole chunk. Shrinking them too changed the last token's logits by ~1e-4 when it sat alone in its 16-token group (likely the 32-token DeltaNet chunk); find that first.
- Decode, kv4a16 attention: `part_q` with kv4 is latency-bound at long context (~91 GB/s at 30.7K). Bandwidth-bound it would save about 3 ms per token at 30K.
- NPU split: back-to-back processes (kld_ref's one process per chunk) intermittently hit an NPU command timeout (TDR, recovered; about 4 in 15 runs, none with the page cache dropped and memory compacted before each run). The npu branch fails the same way. Suspect: page migration evicting the GPU queues while an NPU job waits on the GPU (~200K pages migrate per run although the model copy is all 2 MB pages). The server now runs only native sets, so it needs this fixed.
- NPU attention split (architecture.md, NPU attention): the kernel, the GPU encoders and chained calls are in. Plan: the NPU takes whole KV heads over the keys before the chunk; the GPU encodes a layer's records into one reused buffer and each call's stream reads its own payloads, then the head's shared records (a Loom sender over two bindings); one ready and one done word a layer. The sender (HRX patch 0059), the host-gated runner in `LoomNpu` and the GPU's merge kernels (the key-split pair's NPU twins) are in. The head split in `LoomPrefill` is in (results.md: -6% at 128K kv8, measured on the removed MQ4 A4 path; to redo on UD-IQ4_XS). Left: more KV heads on the NPU (`YAH_NPU_ATTN=2`: with one the NPU is busy ~20% of the time), the server's `--npu` for attention sets, kld_ref against BF16, and Loom's route reset for the image.
- Prefill on HRX main, the depth gap: against the old pin (results.md), plain8 128K is +0.98% (matched pair, 2026-11-15: -2.4% in chunks 0-7, +2.5% in the deepest), npu8x2 16K +1.5%, the combined split at 32K +1.6%. The known part is VOPD pairing: main's `VOPD_INTERLOCK_HAZARD` rule (equal-parity SRC0 / SRC1 reads can lose the forwarding interlock, a correctness hazard) declines pairs the pin issued. In the deep-chunk attention kernel's always-run path the port has 113 `v_dual_mul_f32` and 45 `v_dual_fmac_f32` where the pin has 165 and 119 (about 126 more issue slots per key-block pass); the rescale branch loses 111 more pairs but is skipped when the rescale factor is 1. Main's allocator already prefers different parities for the pairs the scheduler places together (the VOPD pair placement recipes), but in that kernel 240 adjacent candidates still fail only on parity (some source orientation passes the old mod-4 bank rule, none passes parity), unchanged with a 256-VGPR budget. Why they lose: 212 of the 246 parity-only rejections are two multiplies sharing one factor register (a splatted scale or rescale factor), and such a pair needs both other sources to differ in parity from the factor, which half of a WMMA tuple never does. An exact second copy of each factor in the other parity nearly doubles the kernel's dual pairs, but only at 200-209 VGPRs (one workgroup per WGP instead of two); under a 192 budget the gain is gone. Lead: an allocator that keeps those copies within 192 VGPRs. Measured dead ends (2026-11-15, clock-adjusted dispatch profiles): an attention VGPR budget of 188 (184 VGPRs, 64 fewer always-run VALU) ran attention 1.1% slower. The paired kres GEMMs keep a 32-byte prologue spill at 192 VGPRs (the zero accumulator init is spilled, not rematerialized).
- NPU timeouts in kld_ref's launch pattern: on 2026-11-15 about half of kld_ref's process starts hit the NPU command timeout, on both the old pin and HRX main; ordinary launches pass, and `nice` and page cache drops are ruled out as causes.
- Upstream the local HRX patches (see build-and-run.md), with the owner's agreement.
